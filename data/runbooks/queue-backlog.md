# Runbook: 큐 적체(Queue Backlog) 대응 절차

## 증상
- 메시지 큐의 consumer lag나 `ApproximateNumberOfMessagesVisible`이 계속 늘어난다
- 가장 오래된 메시지의 나이(`oldest message age`)가 분 단위에서 시간 단위로 올라간다
- 유입 속도가 소비 속도를 넘고 있거나 컨슈머 인스턴스 수가 줄었다
- Kafka 컨슈머 그룹이 리밸런싱을 반복하거나 일부 파티션에 메시지가 몰려 있다
- 처리 실패가 반복되는 poison message 때문에 DLQ 유입이 늘어난다
- API 응답은 빠른데 메일 발송, 정산, 알림 같은 비동기 후속 처리 결과만 늦게 반영된다
- 컨슈머 자체의 CPU·메모리는 낮고 하위 의존 서비스 호출 시간이 길어졌다
- 요청-응답 지연이 아니라 비동기 처리 지연이라는 점이 응답 지연 절차와 다르다

## 조치 절차
1. get_monitoring_status와 큐 지표로 consumer lag, 가장 오래된 메시지의 나이, 유입/소비 속도를 확인한다.
2. 컨슈머가 죽었거나 리밸런싱을 반복하는지 확인하고, 죽은 인스턴스를 재기동한다.
3. 소비 속도가 유입을 따라가지 못하면 컨슈머 수와 파티션 병렬도를 늘려 적체부터 줄인다.
4. 처리 실패가 반복되는 poison message가 있으면 DLQ로 격리해 나머지 메시지 처리가 막히지 않게 한다.
5. 정상화 후 컨슈머 처리 시간의 병목(하위 의존 서비스)을 분석하고, lag 임계값 알림과 오토스케일링 기준을 설정한다.
