# Runbook: 스레드 풀 고갈(Thread Pool Exhaustion) 대응 절차

## 증상
- `RejectedExecutionException`, `Thread pool is full`, Tomcat `maxThreads reached`가 로그에 찍힌다
- 활성 스레드가 최대치에 붙어 있고 작업 큐가 가득 찼다
- CPU는 낮은데 요청이 큐에서 오래 대기한다 (스레드가 I/O 대기로 묶인 상태)
- 스레드 덤프에서 수백 개 스레드가 같은 외부 API·DB 호출 지점에서 WAITING/BLOCKED이다
- 처음엔 응답이 느려지다가 곧 503이나 즉시 거부로 바뀌고 `/health` 엔드포인트도 응답하지 못한다
- 단순한 응답 지연과 달리 스레드 수가 상한에 고정되고 rejected 카운터가 올라간다
- 하위 서비스 하나가 느려진 시점부터 이 서비스의 요청 전체가 같이 막힌다
- Node/Netty 계열이면 이벤트 루프가 블로킹 호출에 막혀 모든 요청이 멈춘다

## 조치 절차
1. get_monitoring_status로 활성 스레드 수, 작업 큐 길이, 거부(rejected)된 요청 수를 확인하고 CPU가 낮은지 함께 본다.
2. 스레드 덤프(`jstack` 등)를 떠서 대부분의 스레드가 같은 호출 지점(외부 API, DB, 락)에서 WAITING/BLOCKED인지 확인한다.
3. 원인이 되는 의존 서비스가 느리다면 해당 호출에 타임아웃과 서킷 브레이커를 적용해 스레드가 묶이지 않게 한다.
4. 급한 경우 인스턴스를 재시작하거나 늘려 스레드 여유를 확보하되, 풀 크기와 큐 크기는 원인 해결 전에 무작정 키우지 않는다.
5. 정상화 후 의존 서비스별 격리(bulkhead)와 스레드 사용률 알림을 설정해 재발을 조기에 감지한다.
